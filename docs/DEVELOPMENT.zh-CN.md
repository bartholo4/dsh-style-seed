# 开发与验证记录

这份记录概述项目的主要设计、实验和结果。测试数字只适用于所列版本、场景和样本，不等同于长期成功率或答案质量提升。原始私有会话、凭据、请求内容和实验日志不随仓库公开。

## 目标与最初的对照

项目起点是发起人的一次个人使用观察：在同一会话中先使用 Kimi K3.1 PRO，随后切换到 DeepSeek V4.1 Flash，后者延续了自然、围绕任务展开的英文思考风格。这与发起人在 DeepSeek 极简模式下观察到的风格相近，于是开始探索怎样在 DeepSeek Harness 中复现和使用这种体验。这里的模型名称按当时使用时的称呼记录，风格相似是个人观察；本项目没有完成与极简模式的直接对照，也未证明二者内部机制相同。

随后，项目通过对照研究历史对话、思考字段及样例内容对后续输出的影响，再将经测试的思路做成会话级插件。公开示例是在后续样例整理过程中经提供者审阅并同意公开的内容，不应将项目起因等同于对该示例原始来源或内部机制的证明。DSH 插件代码独立实现，没有复用其他工具的运行代码。

项目希望促成的是自然、任务导向的表达，而不是要求每段以固定词语开头。插件使用历史样例作为上下文，不添加“以 We need 开头”的风格指令，也不禁止 “Let me”；这些词语分别用于辅助观察，不是质量判断或模型内部过程的证明。

最初比较了无样例和不同历史组织方式。早期对照并没有证明任意样例都有效。随后发现，不同兼容服务可能读取不同的历史思考字段；在一个固定模型和服务组合中，将历史 assistant 思考放入 `reasoning` 而非默认的 `reasoning_content` 后，观察到更符合目标的表达。服务端接受字段或计入 token，本身不能证明模型内部如何使用它。

## 会话开关与原生流程

早期独立 provider 版本需要显式选择插件提供的模型；之后项目转向与 DSH 会话集成：每个新会话独立控制、默认关闭，并保留用户原本的模型选择。开发中分别检查了会话状态、身份与引用校验、模型配置变化、首轮、续聊、工具调用、重启恢复、图片和配置错误等路径。

在一次较早的 `.5` Web 实验中，使用固定的 d1api DeepSeek 模型与相同的问题，进行 8 对新会话对照：开启样例时 8/8 个首响应以 “We need” 开头、合计出现 0 次 “Let me”，关闭时分别为 3/8 和 9 次。当时使用的是较长的旧样例，并非仓库现在提供的缩短样例。该观察仅覆盖当时的实验版本和单一模型／服务组合；它记录的是措辞风格，没有构成答案质量的盲评，也不能证明当前短样例或其他模型会有相同变化。

## We need 与 Let me：如何统计

为了观察更接近当前公开示例的情况，另一次独立 DSH `0.2.2-alpha.2` 实验使用了与公开示例相同内容的 D 样例，在固定 d1api `deepseek-v4.1-flash`／Max 环境中测试。该实验基于 `experimental.9` 和仅首轮带入的实验钩子，**不是直接测量发布版 `experimental.13`**。下表统计的是协议完整的主响应片段，包含首轮、续聊及工具前后续步；同一会话可贡献多个片段。

| 实验条件 | 完成的会话 | 主响应片段 | 以 “We need” 精确开头 | “Let me” 出现总次数 |
| --- | ---: | ---: | ---: | ---: |
| D 样例仅首轮带入 | 4/4 | 20 | 14 | 0 |
| 关闭开关、无样例 | 2/4 | 18 | 1 | 22 |

“We need” 按片段起始处的精确大小写计数；“Let me” 统计片段任意位置的出现次数、忽略大小写。关闭组另有两个会话在首轮被工具守卫中止，表中包含中止前协议完整的片段，不能当作四个完整会话。仅比较两组均完成的两个场景，各组均为 2 个会话、10 个片段：样例组有 7 个 “We need” 开头、0 次 “Let me”，无样例组分别为 1 个和 3 次。

这组结果说明，即使在这批样例组中，6 个片段也没有以 “We need” 开头；它并不证明未来都不会出现 “Let me”。开启和关闭组使用的适配器及指令角色不同，且样本量很小、关闭组有中止，不能将差异认定为严格单变量因果结果或推算长期成功率。该实验还发现部分模糊问题会把样例内容误当成真实前文。

## 样例缩短、内容影响与首轮策略

为减少额外上下文，开发过程中尝试缩短多轮样例的回答和思考片段，也比较了更短、更中性的候选。不同样例对风格的影响并不一致；有些中性候选没有达到既定风格目标。

测试同时发现，样例内容可能串入真实回答：在一次模糊自检中，模型把样例里的盒子题当成了真实对话。后续将新会话改为只在第一个成功答复前直接发送样例；这减少后续重复发送，但无法撤销样例对首答的影响，也不能保证续聊完全不受影响。

仓库提供的示例是经提供者审阅并同意公开的两轮内容；个人路径和内部来源记录已去除。样例的有效性依赖具体模型、服务和上下文，请独立判断是否适合自己的任务。

## 图片、超时与跟随所选模型

Web 试用曾因插件拒绝工具返回的图片而报错。后续加入用户图片和工具图片的处理，并通过合成宿主流程及两次真实合成图片请求进行有限验证；不同版本、最终代码和不同测试条件应分别看待。

请求总时限后来交回宿主和所选服务处理；当前跟随所选 provider 的版本不再自行设置此前的 120 秒总时限。各 provider、服务端或客户端仍可能设置自己的时限。

`0.2.0-experimental.13` 将新会话改为使用 DSH 当前选择的 provider、模型和请求参数，并针对 OpenAI Chat Completions 与 DSH 官方 DeepSeek Messages 实现样例映射。新会话的样例临时加入请求，不写入会话事件；较早版本的持久引用使用单独的兼容处理。

这一内部候选记录了 137 项合成检查，并进行了一次真实 d1api 合成算术请求：请求成功，样例思考字段到达出站请求，答案正确，单次思考以 “We need” 开头。其他服务地址、官方账号、真实用户原会话和桌面日常使用并未因此获得实网验证。公开仓库整理的是可移植测试子集，并非内部 137 项的原样复现；依赖旧实验源码的 `.12` 跨版本迁移等测试未包含。发布前公开回归集以 Node 24.19.0 和 DSH 0.2.2-alpha.2 运行时执行，123 项通过、0 项跳过。

## 发布前复核与仍存在的问题

发布准备中另外使用真实 DSH alpha.2 的部分宿主组件，配合纯内存合成数据和禁网替身，复现了运行中禁用／重载的并发问题：已认领但尚未写入的消息可能失败，或者普通 provider 在未携带样例时完成首答。旧版持久引用在插件移除后还可能作为普通文本标记进入请求。通过这些测试表示**缺陷已被复现**，不表示修复通过。

目前没有证明插件内部能原子阻止宿主在卸载窗口继续接收输入，因此本仓库按实验版公开。维护前应停止所有客户端提交、等待任务和队列结束并正常关闭服务；旧会话的迁移和回退仍需另行处理。参见主 README 的已知限制。

发布前另外使用官方 DSH 0.2.2-alpha.2 CLI，在全新隔离的 DSH home、profile 和包存储中离线执行本地目录安装；该安装为指向隔离源码快照的 `link:`。组合配置中识别了已启用组件和独立合成样例，Web 启动至就绪；没有进行浏览器、RPC 或模型对话的端到端验证，也未验证 tarball 安装。测试通过进程级网络守卫，未观察到连接尝试。

## `.14` 云端优化

在独立安装的官方 DSH `0.2.2-alpha.2` 和 Node `24.22.1` 上，以合成内存会话、真实宿主服务和禁止模型网络的替身测试修复路由准备时的排空：已接收消息恰好提交一次，请求恰好发送一次并含样例，样例正文和思考没有写入新会话事件。关闭阶段只禁止新的开关编辑，不把仍在排空的代理误判为失去所有权。

客户端增加显式只读状态重试，不自动重发结果不确定的 set；覆盖重复失败、重复点击、切换会话和旧响应。完整测试现在要求固定宿主版本且零跳过，可移植测试单列，不再把缺宿主的部分绿色结果当作完整通过。

仍复现最终空闲快照后入队导致样例遗漏，以及卸载后旧引用成为普通文本的边界；没有宣称热卸载安全。验证没有调用付费模型、读取真实凭据或改动用户桌面；没有新增答案质量／能力提升证据。

最终 `npm run check`：140 项通过、0 失败、0 跳过；客户端产物一致性、所有 JavaScript 语法及 diff 空白检查通过。没有独立 lint／TypeScript 工具链；没有进行真实浏览器端到端测试。
