# dsh-style-seed · weneed 开关

[English](README.en.md)

一个面向 [DeepSeek Harness（DSH）](https://github.com/deepseek-ai/deepseek-harness) 的实验性 Web 插件。它为新会话提供独立的 **weneed 开关**：开启后，插件在首轮请求中临时加入经过授权的历史对话及思考样例，希望兼容模型更常采用以任务为中心的英文思考表达，例如 “We need …”。

**状态：实验版。** 项目发起人在自己的使用中观察到，这种思考风格下部分回答质量有所改善；这是一项个人体验，尚未经过足够样本的盲测、跨模型评估或因果验证。插件不能保证出现特定措辞，也不能保证答案更准确、能力更强或成本更低。模型的最终回答仍应按任务独立核对。

> **重要：不要在任务运行或消息排队期间禁用、重载、更新或卸载本插件。** `.14` 已修复已复现的“路由准备中卸载导致已接收消息丢失”问题；但最终空闲快照之后的新输入仍可能让开关显示开启而请求没有携带样例。维护前停止所有客户端提交，等待进行中和排队任务结束，正常关闭相关 DSH 服务并确认进程退出，再操作插件。旧版会话中保留的历史引用还有单独的恢复限制；停服本身不会迁移或清理旧会话。详见[已知限制](#已知限制)与[开发与验证记录](docs/DEVELOPMENT.zh-CN.md)。

## 为什么做这个插件

最初，项目发起人在同一会话中先使用 Kimi K3.1 PRO，随后切换到 DeepSeek V4.1 Flash，观察到后者延续了一种自然的、围绕任务展开的英文思考风格。发起人认为，这与自己在 DeepSeek 极简模式下看到的风格相近。这个现象启发了后续的样例对照、缩短和插件开发，希望在 DSH 中更方便地尝试这种风格。极简模式的相似性是个人使用观察；本项目尚未对两种方式进行直接对照，也不能据此认定内部机制相同。

“We need” 是这种风格中可能出现的表达，不是每个思考段落都必须使用的开头。项目希望模型直接分析任务，减少反复出现 “Let me” 这样的自我指述。插件通过提供示例对话和思考作为上下文来引导模型，**不会添加要求以 “We need” 开头的提示词**，也不强制禁止 “Let me”；实际措辞由模型、任务和上下文共同决定。

一次使用与公开样例相同内容的早期实验中，4 个会话产生的 20 个主响应片段里，14 个以 “We need” 开头，合计出现 0 次 “Let me”。这些片段包含工具续步，并非 20 个独立会话；该实验使用试验钩子，不是对发布版 `.13` 的直接测量。对照组的中止情况和其他限制见[开发与验证记录](docs/DEVELOPMENT.zh-CN.md)。

## 功能

- 每个新会话的开关默认关闭；选择模型后，可在发送首条消息前手动开启。
- 开启后沿用 DSH 当前选择的服务、模型和请求参数；不要求固定某个中转站或模型名称。
- 在第一个成功答复之前，将样例作为临时历史加入请求；首轮涉及工具调用时，相应续步仍带样例。首答完成后不再直接加入该样例。
- 新会话的样例正文不写入会话事件；开关状态及必要的校验信息由插件保存。样例会发送给所选模型服务，切勿把不愿提供给该服务的信息放进样例。
- 会话空闲时可关闭开关；开始过的会话关闭后不能在同一会话重新开启，需要新建会话。
- 提供已获授权公开的[示例样例](examples/we-need-seed.json)。你也可以使用符合格式、且有权使用的其他样例。

## 安装与配置

建议先使用隔离的测试环境，并备份需要保留的配置和会话。以下采用 DSH 的标准本地目录安装形式；不要在运行中的 profile 上直接热更新插件。

```bash
git clone https://github.com/bartholo4/dsh-style-seed.git
cd dsh-style-seed
dsh plugin --profile web add .
```

`web` 是示例 profile 名称；如果你的 `web` 已有重要数据，请先做好备份或使用独立测试环境。DSH 的 profile 与插件管理规则请参考[对应版本的官方 CLI 文档](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.2-alpha.2/apps/cli/reference/README.md)。本项目通过 GitHub 分发，尚未发布到 npm。

组件安装后默认不启用。通过 DSH 官方配置界面，或在所用 profile 的 `cordis.patch.yml` 中配置该组件；如果文件已有同一 `id` 的条目，应修改现有条目，避免创建重复项：

```yaml
- id: dsh-style-seed
  config:
    enabled: true
    followSelected: true
    seedPath: "/absolute/path/to/dsh-style-seed/examples/we-need-seed.json"
```

将 `seedPath` 换成**本机实际存在的绝对路径**。Windows 可使用例如 `C:/path/to/...` 的绝对路径。`seedPath` 缺失或文件格式不合法时，组件不会正常启用。配置服务商和凭据仍使用 DSH 自己的方式，勿把真实密钥写进此仓库或样例。

完成配置后，按上面的维护顺序关闭并重新启动所用 DSH Web profile。新建会话，选择模型，再按需打开输入区的 **weneed 开关**。不适合当前模型或接口时，等待当前任务结束后关闭开关；已开始的会话若需再次开启，请新建会话。

发布前已在隔离环境中，用 DSH 0.2.2-alpha.2 官方 CLI 离线执行 `add .`，并以合成样例启动 Web 至就绪。该次安装是链接本地源码快照；没有进行浏览器、RPC 或模型对话的端到端验证，也不能替代对其他 DSH 版本的验证。

## 工作原理

1. 插件在宿主中注册会话开关，识别符合条件的新顶层会话，并读取经校验的外置样例。
2. 对开启的首轮请求，插件核对当前选择的 provider、模型及其配置，将样例投影为临时用户／助手消息，并通过所选原生适配器发送。OpenAI 兼容路径使用临时适配元数据选择历史思考字段；该字段选择标记不是密码学签名。
3. 样例只在第一个成功答复前的主请求及必要工具续步中直接加入。它可能影响首答；即使后续不再发送原样例，首答本身仍会留在会话里并影响续聊。
4. 不支持或无法核验的路由会报错或要求关闭开关；关闭后的行为仍受所选 DSH provider 和旧会话兼容限制约束。

插件不向模型添加“必须以 We need 开头”的风格指令，也不保证服务商一定支持或使用历史思考字段。兼容接口接受请求并不单独证明模型实际利用了样例。

## 测试与开发过程

项目经历了历史思考字段对照、会话级开关、样例缩短与仅首轮注入、图片和工具处理、请求超时调整，以及跟随所选模型的适配。早期 `.5` 版使用**较长的旧样例**，在固定模型环境的 8 对新会话里，开启组首响应 8/8 以 “We need” 开头、合计 0 次 “Let me”，关闭组分别为 3/8 和 9 次；这只是小样本的风格观察，不是答案质量评测，也不能作为当前公开短样例效果的证明。原 `.13` 内部候选曾完成 137 项合成检查及一次真实合成请求；不同阶段和版本的结果不应混算。

完整时间线、测试方法、失败与未验证项见[开发与验证记录](docs/DEVELOPMENT.zh-CN.md)。公开仓库的测试是整理后的可移植子集，并非上述内部 137 项的原样复现；例如依赖旧实验源码的 `.12` 跨版本迁移测试未公开。发布前用 Node 24.19.0 和 DSH 0.2.2-alpha.2 运行时执行了公开回归集，123 项通过、0 项跳过。测试均使用合成输入；依赖真实 DSH 宿主的测试需要显式提供对应版本的运行时。在克隆的仓库源码目录中运行：

```bash
npm run check:client
npm test
```

若要运行依赖宿主的合成集成测试，将环境变量 `DSH_RUNTIME_NODE_MODULES` 指向 **DSH 0.2.2-alpha.2** 安装中的 `node_modules` 后再运行 `npm test`。`npm test` 现在会在未设置、版本不匹配或测试有跳过时失败；只需可移植检查时请显式使用 `npm run test:portable`，这不是完整验证。客户端资源可使用 `npm run build:client` 重新生成。

`npm run test:lifecycle` 单独运行生命周期检查，需要同一运行时变量。其中已修复场景使用正向回归断言，仍存在的边界明确标为 `KNOWN BOUNDARY`；通过这些边界表征不代表热卸载安全。 测试使用合成数据并禁止真实网络。

## 已知限制

- **运行中维护竞态：**已修复路由准备期间因关闭门禁而拒绝已接收输入的路径，并保持已接受请求的样例与拦截器直到排队任务排空；但最终空闲快照后的新提交仍可能让开启状态与实际发送不一致。上方停服步骤是使用限制，不等于问题已经修复。
- **旧会话：**较早版本可能留下签名历史引用。卸载或回退后继续使用旧会话可能发送普通标记或无法恢复原先行为；请保留备份，并按需要新建会话，不要认为停服即可自动迁移。
- **样例影响回答：**在一次早期测试中，模糊的自检问题把样例中的盒子题误当成真实对话。仅首轮加入样例不能保证消除这种影响。
- **效果与覆盖范围：**风格受模型、服务商、参数、任务和上下文影响；本项目不保证稳定触发或提升质量。长会话、其他服务商实网和完整桌面使用仍需验证。
- **维护与回退：**签名密钥生命周期、跨版本回退及卸载后的完整恢复尚未形成通用方案。请勿在没有可用备份和隔离验证时用于重要会话。

### `.14` 开发检查与错误恢复

`.14` 云端最终检查使用 Node `24.22.1` 与实际安装的 DSH `0.2.2-alpha.2`：**142 项通过，0 失败，0 跳过**。覆盖真实宿主服务和网关 RPC、合成模型响应及确定性客户端组件／产物测试；自动化集本身不等于浏览器或付费模型验证。另以真实云端 Web UI 连接 loopback mock 服务，验证默认关闭、首个成功答复带样例、后续不带样例、安全的未知工具续步、失败后重试、停止／取消后重试及关闭后恢复。取消首答问题修复后已重新实测：同一开启会话重试带样例，成功后下一轮不带；7 个隔离会话共 197 条记录未发现样例正文／思考的精确字符串。这是实际 UI／协议测试，但响应为 mock，不证明模型效果。

完整检查：设置上述宿主运行时后执行 `npm run check`（客户端产物一致性 + 严格完整测试）。CI 安装固定版本的官方 DSH 后运行同一命令。本仓库为 JavaScript，没有单独的 TypeScript 或 lint 配置。

RPC 出错后显示“重试检查”，只重新读取服务端状态，不会重发结果不确定的开关写入；切换会话、旧响应和重复点击仍受代际检查保护。

已知上下文窗口的开启请求需要明确输出 token 上限来保守预留预算。官方 pi-ai 适配器应配置模型级 `models[].maxTokens`（例如隔离测试配置中的 `2048`）；仅配置 provider 级 `defaultMaxTokens` 不一定会给宿主请求提供具体上限。缺失时现在提示配置问题，而不是误报上下文已满；插件不会自行更改所选模型的请求上限。取消首答后留下的原生纯思考片段也不再误按旧版导入记录修复，允许同会话继续重试。

### 有限实网验证

2026-11-01，实际云端 Web UI 在 d1api `deepseek-v4.1-flash`／max 思考下完成算术、排程和严格 JSON 三对 OFF/ON 小样本，六个结果均满足对应测试要求。“We need” 开头为 OFF 1/3、ON 3/3；关闭时也会自然出现，开启也不保证稳定触发。输出 token 有增有减，缓存和计时条件不同，**不能据此宣称更聪明、质量更高、更快或更省**。首个 OFF 请求虽在 UI／服务端显示完成，QA 守卫的终止标记记录仍有不确定性，未回写为确定成功；第 2–6 个请求有完整终止记录。14 个隔离实网会话文件共 281 条记录未发现样例正文／思考精确字符串，但不代表完全没有语义影响。验证后已清理临时实网凭据存储和运行数据。见[完整范围与限制](docs/VALIDATION-2026-11-01.md)。
